### Hardware and installation

Use an idle **MI300X 192 GB, gfx942**, with a working AMD driver and Linux access
to the GPU. The original host reported 205,822,885,888 bytes of VRAM. A 128 GB
MI300A is not sufficient for this full-table configuration. The runner serializes
the original eight logical rank microbatches on one physical GPU; it preserves
the global optimizer update size.

The recorded environment is Python **3.12.3**, PyTorch **2.10.0+rocm7.1**, HIP
**7.1.25424**, and Triton **3.6.0** on x86-64 Linux. Use Python 3.12.3 for the
strict environment check. Start from a host with `python3.12-venv`, Python
development headers and a C/C++ build toolchain available. GPU clock/power limits,
host load and compilation caches affect wall time; the package does not promise
bitwise-identical losses or identical update counts on another host.

```bash
git clone --single-branch --branch repro/mi300x-ks3-v2-20261026 https://github.com/curvedinf/modded-nanogpt.git
cd modded-nanogpt
python3.12 -m venv .venv-mi300
.venv-mi300/bin/python -m pip install --require-hashes -r reproductions/pr393_ks3_v2/requirements.txt
.venv-mi300/bin/python -m pip check
```

On a multi-GPU host, expose one idle MI300X with `ROCR_VISIBLE_DEVICES=0` (select
the appropriate index). The `run` command checks the visible GPU, memory, HIP
build, Python version and all locked package versions before launching. The
installation requirements also pin the SHA256 of each resolved CPython 3.12
Linux wheel; [wheels.json](reproductions/pr393_ks3_v2/wheels.json) records their
download URLs.

### Download and verify the original data

```bash
.venv-mi300/bin/python reproduce_mi300.py download
.venv-mi300/bin/python reproduce_mi300.py verify --environment
```

The downloader pins `kjj0/fineweb10B-gpt2` to revision
`889765ea1f903759787add96995d81171b632d0c`: training shards 1–9 and validation
shard 0, totaling approximately 2 GB. Every shard has a recorded size and SHA256
verified against the original files and that revision's LFS metadata. GPT-2
tokenizer assets are also downloaded and checksum-checked before training.
See [data.json](reproductions/pr393_ks3_v2/data.json). Downloads need network
access; prepared runs use the local data/tokenizer cache. A cold PyTorch/Triton
cache will compile kernels during setup and warmup.

For data on another disk, pass `--data-root /your/data/root` to `download`,
`verify`, `prepare`, and `run`. Files live under
`/your/data/root/data/fineweb10B/`, matching the original `DATA_PATH` semantics.
Extra matching training or validation shards are rejected, so the loader cannot
silently consume a different dataset. Existing files with incorrect hashes are
reported rather than overwritten.

### Run the control and the three KS3 seeds

```bash
.venv-mi300/bin/python reproduce_mi300.py run --model mlp --output logs/reproduced-comparison
.venv-mi300/bin/python reproduce_mi300.py run --model ks3 --output logs/reproduced-comparison
.venv-mi300/bin/python reproduce_mi300.py summary --output logs/reproduced-comparison
```

The first command runs seed 169 once. The second runs seeds 369, 370 and 371
sequentially with the same frozen KS3 recipe. To reproduce only the best seed,
add `--seeds 370`. Each run has a nominal **900-second training budget** and
then full **10,485,760-token validation**. Initialization, original warmup and
final validation add wall time outside the reported training duration. The
timer includes fixed-text probes (1,048,576 tokens every 120 seconds), diagnostics,
probe setup/restoration and final validation setup. Raw weights, BF16 evaluation,
640/1408 attention windows and the fixed YaRN state are used; canonical masking,
tail shipping and final window extension are disabled. A separate reserved-text
confirmation follows final scoring. The run finishes by the original predictive
time-cap rule, not by selecting a step count or training until a chosen loss.

These requested reproductions are exempt from comparative pruning so each seed
can finish. Nonfinite loss, process errors and explicit STOP still terminate a
run. This launcher starts no manager, automatic optimization, or extra seeds.
It uses the original trainer and controller directly; systemd, Codex and SSH
session services are unnecessary. Run inside `tmux` if disconnecting.

Each invocation creates new run IDs, with logs under the selected output path:

- `latest-run.json` and `registry.jsonl`: independent progress and run discovery.
- `runs/<id>/run.json`, `config.json`, `environment.json`, `console.log`,
  `events.jsonl`, and `result.json`: exact launch metadata and measurements.
- `results/`: copied config, events and result for each completed run.
- `summary.json`: full-validation loss, elapsed time, per-arm statistics and
  comparisons against the published MLP and any newly reproduced MLP controls.

The output path is rebuilt for the current checkout; historical absolute paths
are never executed. Original committed measurements remain unchanged. Ctrl-C,
SIGTERM, or `touch logs/reproduced-comparison/STOP` stops the controller and its
training process group. A STOP marker is never removed automatically; use a new
output directory for a separate authorized run. The launcher shares the existing
GPU lease when used in a checkout with active research.

`prepare` requires downloaded data and creates reviewable commands/configs without
importing PyTorch or starting GPU work. The tests cover source/data corruption,
path relocation, frozen recipe/evaluation parity, stop handling and result
accounting. These checks establish packaging integrity; they do not replace a
fresh full convergence run on the destination MI300X. Full trained checkpoints
are not distributed; these commands retrain from the recorded seeds.

## Preserved and changed

| Setting | Record on 8 H100s | This trainer on 1 MI300X |
|---|---|---|
| Architecture | 11 layers, width 768, 6 heads, MLP 2816 | Same, including mixed head widths and inactive sublayers |
| Hashed bigram/trigram table | 84,602,880 rows × 768, distributed | Same full table, resident on one GPU |
| Batch tokens by stage | 131072 / 262144 / 393216 / 327680 / 131072 | 16384 / 32768 / 49152 / 40960 / 16384 |
| Training steps | 1194 | 1194 |
| Total presented training tokens | 328,663,040 | 41,082,880 |
| Stage boundaries | 0 / 320 / 681 / 1107 / 1174 / 1194 | Same |
| Sequence lengths | 896 / 2048 / 3072 / 3072 / 3072 | Same, with the same 2560-token training attention cap |
| Attention windows and YaRN | Short/long window schedule; final long window 2560 | Same |
| Optimizers | ANVIL + Adam; sparse embedding updates | Same update equations, learning rates, moments, cadence, decay, and embedding split at step 1175 |
| Auxiliary objectives | MTP, prefix prediction, scheduled sampled softmax | Same schedules and candidate construction |
| Final averages and masking | Four tail averages, canonical token mask | Same |
| Precision and execution | Hopper FP8, patched FA3, CUDA graphs | BF16, differentiable PyTorch SDPA, checkpointed MLP/loss, eager model |
| Validation | 10,485,760 tokens, 262144 per rank | Same token count, 262144 per batch on one GPU |
| Initialization seed | Random unless specified | 0; override with `--seed N` |

This is a runnable single-GPU baseline, not a reproduction of the record's convergence or time.
It uses one original rank's token batch per optimizer step, with no accumulation to recreate
an eight-GPU global batch. The LR schedule is intentionally retained, not retuned for the smaller
batch. BF16 replaces the record's FP8 quantization and straight-through gradients; the loss uses
the exact differentiable softcap and excludes unavailable future MTP targets at the batch tail.
The source CUDA kernel has slightly different rounding and tail-gradient behavior. A 3.28 result
is not established by smoke tests.

Attention keeps document boundaries, paired heads, QK normalization, partial key offset, and
explicit attention scale. It partitions queries into 256-token chunks while retaining the complete
allowed key window; chunking does not shorten context. MLP and 1024-row loss slabs use activation
recomputation to bound memory. ANVIL's spectral products use ROCm-native matrix multiplication;
the other portable sparse/optimizer Triton kernels are retained. Communication APIs use a one-rank
RCCL/Gloo group. Loopback rendezvous avoids this droplet's numeric-hostname resolution issue.

For a smaller-memory experiment, `MI300_NGRAM_ROWS=10575360 ./run_mi300.sh` reduces the hash table
to one original rank's storage. This changes model capacity and hash collisions and is **not the default**.

## Verification commands

```bash
.venv-mi300/bin/python test_mi300.py
./run_mi300.sh --smoke
./run_mi300.sh --smoke-stages
```

The six focused tests cover schedule parity, document/window attention outputs and gradients,
paired rotary embeddings, partial key offset, and full/sampled softmax with MTP/prefix objectives.
`--smoke` runs two real FineWeb training updates and a 1024-token evaluation.
`--smoke-stages` runs 32 real-data updates around every distinct stage, candidate size,
period-4 sparse cadence, twin-rail engagement, and embedding split. It also runs tail averaging
and final-window canonical-mask evaluation on a full 262144-token validation batch. These jump between schedule positions and are
functional checks, not a training-quality experiment. Smoke modes never write checkpoints.
Validation evidence is retained under `logs/mi300-port-validation/`.

## PR393 grouped attention correction, 2026-10-24

Registered probes151–155 found shape-dependent errors in ROCm SDPA with
heterogeneous grouped masks, including the prior KS3 training backend and the
frozen control's training primitive. Explicit FP64 document softmax and gradients
confirmed the errors. Head padding or contiguous head masks alone did not fix all
production stages. Original measurements and controls remain immutable.

The corrected KS3 path uses PyTorch math SDPA only for heterogeneous groups,
native SDPA for equal-shape groups, and tiled local gradients. Pilot156 passed
all five stage shapes against original attention and independent FP64 document
oracles, plus the existing BF16 gradient bounds. Canonical no-grad evaluation
remains on the verified equal-shape path and was bitwise equal to the original
implementation across these checks. All expert, router and geometry updates
passed; peak allocation was163.56GiB. This adaptation changes no compiler flags.

`configs/control393/attention_correction.json` records the evidence. Historical
training proxies have a distinct attention compatibility signature; canonical
full-validation references remain eligible. The strictly-below5 latch and first
one-sided +0.01 pruning rule are unchanged. Full KS3 trials must declare the
verified corrected attention semantics.
